# Architecture

## Components

```
Browser extension ─┐
Web app ───────────┼──► API server (FastAPI) ──► Postgres + pgvector
Your AI assistant ─┘        │  MCP server            (items, notes, chunks,
   (via MCP)                │                         vectors, permissions)
                            ├──► Workers (task queue)
                            │       metadata lookup, parsing, chunking,
                            │       open-access checks, related papers
                            ├──► Model service (separate container, optional GPU)
                            │       embeddings, reranking, OCR
                            └──► Object storage (S3-compatible or filesystem)
                                    PDFs and files, stored by SHA-256

External (read-only): Crossref, OpenAlex, arXiv, PubMed, Unpaywall,
Semantic Scholar (SPECTER2 vectors), Zotero translation-server (optional)
```

The server never calls an LLM vendor. AI reasoning happens in the user's own
client; the server does retrieval, permissions and provenance.

## Stack

| Part | Choice |
| --- | --- |
| API | Python, FastAPI + Pydantic; OpenAPI schema generates the TypeScript client |
| Database | Postgres + pgvector; SQLAlchemy 2 or psycopg; Alembic migrations |
| Task queue | Procrastinate (queue in Postgres, no Redis); alternatives Dramatiq/Celery |
| Model service | Separate container like Immich's ML service: embeddings, reranker, OCR |
| MCP | Official Python SDK, mounted in the same FastAPI app; Streamable HTTP |
| Frontend | TypeScript, SvelteKit (static, served by the API server), PDF.js; client generated with @hey-api/openapi-ts |
| Browser extension | TypeScript, WebExtensions (Chrome + Firefox) |
| Tooling | uv, ruff, ty, pytest |

Rust via PyO3/maturin is an option later for measured hot spots (chunking,
hashing, diffing). Keep those parts pure functions with simple inputs and
outputs. Measure first: the database and models are the likely bottlenecks.

## Data model (first sketch)

IDs: every record (user, item, file, note, annotation, collection, …) has a
UUIDv7 primary key, generated by Postgres (`uuidv7()`) or by a client. Time
ordered, so indexes stay compact; not guessable; no collisions when merging
or importing libraries. Content hashes are used only where content is the
identity: blobs and chunks.

Three levels: an **item** is the work, a **version** is one edition of it,
a **file** is concrete bytes.

```
Item: the work; notes, tags, collections, citation metadata
├─ Version: preprint    identifiers (arXiv, DOI), metadata from the registry
│    └─ File (main): preprint.pdf
└─ Version: published   identifiers (DOI), metadata from the registry
     ├─ File (main): published.pdf
     └─ File (supplementary): data.zip
```

- **Item**: one work (paper, book, thesis, report, lecture notes, slides,
  meeting notes, method, dataset, code). Metadata is CSL-JSON; item types
  follow CSL (e.g. meeting notes: `document` with `genre`). The metadata for
  citing is the preferred version's metadata plus the item's manual edits
  (per field, never overwritten by a lookup). Notes, tags and collections
  belong to the item.
- **Version**: one edition of the work. Kind: draft, submitted, preprint,
  accepted, published, edition (with a label such as "WS 2025/26" or
  "2nd edition"), other. Own metadata (CSL-JSON) and where it came from
  (identifier lookup, manual, import, sync). Can exist without files
  (metadata only). Preferred version: pinned by the user, otherwise
  published > accepted > edition > submitted > preprint > draft > other,
  newest first. Items with one form (meeting notes) have one version.
- **Identifier**: (scheme, value) of a version, normalized: DOI, arXiv,
  ISBN, PMID, URL, git (repo + path). Unique across the library, so adding a
  known identifier finds the existing item, whatever the scheme.
- **File**: a record with its own UUID, belongs to a version, points to a
  blob. Role: main, supplementary, slides, transcript, recording, other.
  The same blob can back several files, each with its own permissions,
  provenance and annotations.
- **Blob**: the bytes of a file, stored once by SHA-256;
  garbage-collected when no file record uses it.
- **Content manifest**: ordered list of chunk hashes for a file; one per
  revision for synced files (e.g. lecture notes from git), so frequent
  updates stay cheap.
- **Chunk**: paragraph-sized text, stored once per content hash, with page and
  position anchors, section path and type (body, caption, abstract, note,
  annotation).
- **Embedding**: per (chunk hash, model ID).
- **Note**: Markdown, linked to items and passages; owner + visibility.
- **Annotation**: W3C Web Annotation model, anchored by text quote selector
  plus page coordinates.
- **Person** (later): an author or editor, so people can click a name and
  see all of that person's items in the library. Linked from items by
  position and role (author, editor, …); the CSL-JSON stays as it is.
  Matching: ORCID first (Crossref and DataCite often include it), then
  OpenAlex author IDs, then normalized names ("Huber, A." vs "Anna Huber")
  only as a suggestion. Users can merge and split people, since names are
  ambiguous both ways (two people, one name; one person, several spellings).
- **Collection, tag, group, membership, role.**
- **Provenance**: who or what created each object (user, AI via client X,
  import, sync), for labels, the AI inbox and the audit log.

Every chunk and note carries owner and visibility, so permission filters run
inside the search query itself.

### Changes, sync and trash

- **Change numbers**: each transaction that changes an item (or its
  versions, identifiers, files) stamps it with the next number of a
  per-library counter. The counter row stays locked until commit, so
  numbers appear in order. `GET /api/items?since=N` returns everything
  changed after N; the `Last-Change` header is the next N. Notes,
  annotations and collections get change numbers the same way.
- **Concurrent edits**: responses carry `ETag` (the change number); edits
  need `If-Match` (428 without, 412 if someone changed the item meanwhile).
  The client then re-reads and merges, like Zotero's per-field merge.
- **Trash**: deleting moves items and files to the trash (`deleted_at`);
  sync clients see that as a change. Emptying the trash later must leave
  tombstones (id + change number) so sync clients learn about it.

## Scaling notes

- pgvector limits (from memory, verify): `vector` indexable up to 2,000
  dimensions, `halfvec` up to 4,000, storable up to 16,000.
- Rough memory at 1,024 dimensions as `halfvec`: one group (~500k vectors)
  ~1 GB; a department (~5M) ~10–15 GB; a whole university (~50M) 100+ GB.
- For a group, exact search without an index is fast (tens of ms) and always
  correct with permission filters. Add HNSW later, with iterative index scans
  (pgvector 0.8+), possibly partial indexes per group.
- Beyond tens of millions of vectors: pgvectorscale (DiskANN) or binary
  quantization with re-scoring.
